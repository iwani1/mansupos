# Phase 1 reliability safeguards — isolated development draft

**Status: code, fixture tests and isolated demo-browser checks only. Not a deployment, pilot migration, live-order test, or trading approval.** The existing read-only pilot, online WooCommerce/Paystack shop, and any other VPS app have not been changed by this work. Do not pull this branch into the pilot, run its preflight/migrations on the pilot ledger, bind a real ledger, install a trading unit, enable any write gate, create a real order, or restore over a live database on the strength of these tests. The owner-reported pilot version/backup status has not been independently rechecked. This branch still requires owner review, a maintenance plan, independently verified backups and the separate live acceptance steps in [LIVE-CASH-ROLLOUT.md](LIVE-CASH-ROLLOUT.md).

## What the draft changes

- **Ledger v9:** checks historical Woo order IDs, orphaned sale/shift and foreign-key references before adding a unique non-null Woo-order link. Conflicts stop the migration without deleting or remapping receipts, `trade` rows, saved buyers, shifts or stock. The sale-event and audit journals and cash movements are append-only; a closed shift's recorded count and summary cannot be edited or given a backdated cash movement. These SQLite triggers deter accidental application edits; they are not cryptographic proof against an administrator with direct database access. An invalid historical ledger is a stop-and-review case, not something to repair automatically.
- **Service identity:** a separate `service_identity` (`live-pilot` versus `live-trading`) and ledger UUID are stored in each POS ledger. The live service will refuse to open an *existing, unbound* pre-v9 ledger: it must first be independently reviewed and explicitly bound to the correct service using an unchanged verified snapshot while that service is stopped. Normal startup and restore never silently perform this binding. A v9 ledger missing its identity also fails closed; an existing ledger without a recorded mode is not silently designated demo/staging/live on startup. Even matching service names are insufficient to restore across different ledger UUIDs. Keep pilot and trading data directories, accounts and backup destinations separate; a copied pilot database is not a trading bootstrap.
- **Backup and restore (repaired locally, unreviewed for deployment):** `server/backup.js` creates a consistent SQLite snapshot plus a matching `.db.manifest.json` with size, SHA-256, schema, service/UUID, foreign-key check and sale counts. Keep **both** files together in protected, encrypted off-host storage. The generic `deploy/backup.sh` wrapper preserves backups by default; explicit `RETENTION_DAYS` prunes manifested pairs and needs a separate reviewed retention/off-host policy. `server/restore.js` requires a matching manifest for live/v9 snapshots, checks the staged image against the verified original, and rejects a missing/incomplete required ledger schema, orphan references, a wrong service/UUID or a running instance. It now compares **protected records in both directions**: newer/changed active records AND backup-only records (including a deleted user or receipt) refuse same-ledger replacement. There is no force flag. An allowed replacement first makes a separate verified safety snapshot with its own manifest. Before publishing, it clears backed-up sessions, sets **every real restored user inactive with an unusable password hash**, records a restore lock and audit event. Startup and preflight refuse the locked ledger even if old bootstrap credentials are configured. A fresh restore into an empty isolated directory has no active history for comparison and is **also** quarantined. Restoring does not automatically reauthorize any user; use the separate, explicitly approved stopped-service owner recovery described below. The original backup and safety snapshot are not modified by this quarantine. Pre-mode v1/v2 backups cannot be restored by this guarded tool; preserve them for separately planned historical recovery. Do not treat local comparison as evidence that WooCommerce, external payments or physical cash are unchanged: those systems require independent reconciliation. Back up WordPress files and database separately. Power-loss during file replacement, off-host copies, the actual site and real cash have not been tested. Never restore an older backup to clear an uncertain sale; compare both ledgers and Woo/cash before any approved restore or restart.
- **Checkout recovery:** local prepare, cart snapshot, Woo create, payment, cancellation and wholesale-reprice intents have append-only events. The local row, audit and event commits are transactional; remote writes are not retried automatically. A new Woo-order link requires a prior durable local create intent as well as the exact checkout key, origin and cashier markers, the expected cart/tax/total and the same order identity. Conflicting orders or incomplete key searches (including missing/inconsistent Woo pagination totals) require manual reconciliation. A saved POS payment intent and matching Woo payment record are required before an interrupted payment can be recovered as paid; neither proves a physical cash refund payout. Changed products, amounts, remote status, missing refund amounts and an unexpected cancellation block goods release. Existing cash-only live scope, Woo-stock rechecks, idempotency keys, separate wholesale approval and the pilot's product-only read gate remain in force.
- **Review access:** owner/manager `GET /api/recovery/queue` lists pending/uncertain sales and observed cash refunds with `hasMore`/`nextCursor` pagination (pass `?limit=200&cursor=...` for later pages); `GET /api/sales/:id/events` shows the append-only non-secret event trail. These are API review routes, **not** a dedicated paginated recovery-queue screen. Cashiers cannot access them or the owner audit log. Sale details warn about a cash refund. A refund observation does **not** prove anyone physically paid cash out. Neither endpoint can approve a refund or make a remote write.

## Offline owner recovery after an approved restore — not normal startup

**No production procedure was run or authorized by these tests.** The restored ledger is deliberately unavailable until an owner separately approves offline access recovery. This is not a way to override a refused protected-record comparison; inspect the newer active ledger and Woo/cash evidence instead. On an approved **isolated local copy**, or later only under a separate production change plan:

1. Stop the **exact** POS service and independently check the service identity, `POS_MODE`, `POS_DATA_DIR`, restored ledger UUID, verified backup + manifest, safety image, other POS/WordPress backups, and outstanding Woo orders, refunds, stock and physical cash. Do not edit or delete any ledger or safety image. If identity or business history does not match, **stop**; do not run the recovery command.
2. Have the owner approve the recovery and independently identify an **existing** owner username in this ledger. The tool does not create a new user or choose one automatically. Prepare a **genuinely new, never-reused** strong temporary password (12–256 characters) as one line in an absolute-path **0600 regular file owned by the recovery operator outside the Git checkout and POS data/backups**. The tool cannot compare it with old hashes (they were erased during quarantine), so independently choose a fresh secret and arrange a secure out-of-band owner handoff. Do not put passwords in a command argument, chat, Git, logs, `.env`, or this guide. A private operator editor is appropriate; do not send the file to anyone.
3. With the stopped service's **verified private environment** loaded by an authorized administrator, run `node server/recover-restored-owner.js --confirm-restored-owner OWNER_USERNAME /absolute/private/new-owner-password-file` from the reviewed application checkout. Replace only the two placeholders privately. The command takes an exclusive data-volume lease and refuses a running POS, a missing/incomplete lock, wrong service/identity/schema, an unverified owner, a replay, a weak/insecure password file or a demo ledger. Do not assume a bare checkout shell inherits the service's environment (it may default to demo).
4. Check the exit code and a **read-only** `node server/preflight.js` with the same verified environment; do not proceed if a restore-lock or identity check still fails. After securely handing the new secret to the owner and privately removing the temporary password file, the selected owner may sign in and must change it immediately. The owner must individually verify each disabled staff identity, reset that person's password **before** any activation, and explicitly authorize it. No pre-restore password or session becomes valid again. Do not hand goods over or open selling gates while cash, order, tax, stock, backup or other acceptance remains unresolved.

A normal sign-in cannot bypass the quarantine, and clearing the marker directly in SQLite is **not** a recovery procedure. The audit retains the restored user IDs and earlier sales/shift history; quarantine does not reconcile Woo-only work or physical money. Any unrecognized or changed historical account requires incident review rather than automatic reactivation. The **demo-only** sample ledger has a separate passwordless sample route and is exempt from real-account recovery.

## Cash refund and shift boundary — owner decision still required

A Woo refund reduces the *net-sales report* after reconciliation, but it does **not** establish cash actually left the till. The current draft uses **gross cash received** (plus opening float and separately recorded cash movements) for an **open** shift's expected drawer; it does not subtract a Woo refund automatically. If a previously paid receipt later needs reconciliation, its recorded cash stays in the open drawer and its historical report row remains visible with a review warning; the shift cannot close until that discrepancy is resolved. An interrupted, unconfirmed payment does not become confirmed cash merely by entering a payment method. Already-closed shifts keep their original expected/count/variance/summary even if Woo changes later. Observed cash refunds are surfaced for owner review, including their original sale shift; a disappearing remote refund is flagged without erasing the last POS observation. The generic cash-out facility still exists for ordinary, documented drawer movements, but it must **not** be treated as an approved refund workflow merely because Woo says refunded. In particular, do not backdate a movement into a closed shift or infer that a later shift made the payout. A real payout during an open shift without a separately approved and recorded cash procedure will appear as a count variance; preserve the count and investigate it rather than altering history. The changed open-shift formula must be assessed against any historical *open* shift before a future cutover.

**Owner must decide and document before cash-refund operations:** who authorizes and actually makes each cash payout; what evidence and receipt identify it; whether, when and how an actual later-shift payout affects that later drawer; how partial/repeated/changed Woo refunds and amounts not paid in cash are handled; who resolves a variance; and whether a dedicated refund-to-shift record is required rather than a generic movement. This draft neither selects nor implements that policy. Do not claim that `refund.observed`, net reporting or a Woo status proves payout.

## Isolated verification and remaining acceptance

Fixture tests use temporary SQLite directories and in-memory Woo adapters; browser checks use isolated demo servers. The v8→v9 tests include retained historical trade/buyer rows, refusal of duplicate Woo links and orphans, explicit legacy binding, different-service/UUID restore refusal, checksum/manifest checks, a safety copy, refusal of newer sale/event rollbacks, partial-schema refusal, restored-session revocation and restart after a bootstrap error. Recovery tests include lost create/payment responses across isolated app restarts, remote drift, role boundaries, queue pagination, refund-after-close and refund-before-close scenarios. Use `npm test`, `npm run lint`, `npm run build:live`, and isolated browser checks; the PWA test must run against an isolated **built** demo, not the Vite development server. Passing fixtures do not verify the installed pilot, actual WooCommerce tax or stock effects, off-host restoration, real cash, last-unit concurrency, device hardware, plugins, notifications or the unresolved refund procedure. Record those as **not tested**, not pass. No production or pilot changes are authorized by this document.
