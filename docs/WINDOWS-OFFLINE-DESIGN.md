# Windows till / shared Woo stock — implementation draft, NOT a release

**Status:** Code is on this branch only. The existing web POS and its installed read-only 1.2.3 catalogue pilot are unchanged. The Woo reservation plugin in `woocommerce/mansu-offline-reservations/` is **not installed**. No staging store is available; the intended deployment has **one offline Windows computer**. No Windows installer has been verified on a real computer, no Woo allocation or order has been created on the website, and no live last-unit test has been witnessed. Do not install the plugin, put a write key on the pilot, enable offline selling, or distribute an installer as a public release from this document.

## What the code does in isolation

- `npm run build:desktop` bundles the existing React POS for a private `app://mansu/` Electron window, with relative local fonts/assets and no demo illustrations. The web build and its online-only PWA behavior remain separate. Electron's renderer has a narrow preload IPC bridge; all HTTPS calls originate in the main process and target only the proposed, exactly pinned trading POS origin. The renderer cannot access the filesystem, SQLite, WordPress credentials or a generic network proxy. The central HTTPS origin is pinned to the **proposed** `https://trading.mansutrendzgh.com` host (not the existing `pos.mansutrendzgh.com` pilot or the Woo storefront); its DNS/TLS is **not configured or approved**. Changing that origin requires a reviewed new build. The shell requires Windows DPAPI and refuses a plaintext fallback.
- A **separate** central trading POS service records one active device UUID, delivers a fresh Woo catalogue plus verified allocations, and receives device-HMAC-signed sales/returns. A UUID is **not hardware attestation**: do not clone a Windows profile/ledger onto two active tills or treat this record as proof that only one machine exists. The desktop stores the derived signing secret and central session token sealed with Windows DPAPI. Local staff can sign in from previously provisioned password hashes for 24 hours after online authentication; once that staff window expires, reconnect online before viewing or syncing protected records. The separate stock lease may expire earlier and blocks **new** checkout, not an already authenticated user's inspection of committed receipts or pending sync events. After a stock lease has expired, an online re-sign-in with queued receipts refreshes credentials **without** replacing local allocations or renewing selling authority; sync the original events, then explicitly refresh Woo stock. A reversed clock, a missing allocation, backorders or unknown stock also block new checkout.
- When specifically authorized, an owner allocates managed Woo stock to that device. The **uninstalled** plugin draft subtracts it from the public Woo pool and records the grant in a transaction; it checks current `_stock` **minus checkout-held units** while locking Woo's stock row. Parent-managed variations use one shared pool. Allocation requests are sealed in the local SQLite ledger **before** network I/O. If a response is lost, the original ID survives app restarts and must be retried unchanged; the UI blocks a fresh ID until it is reconciled.
- A new desktop checkout is **cash-only**. Preparing a cart does not spend stock or record money. Confirming cash atomically commits the local sale, allocated-unit movements and an encrypted, ordered sync event in SQLite (WAL with full synchronous commits). Returns require management, physically returned goods and a recorded cash refund. An unverified MoMo or card reference cannot create a new offline sale; historic unverified events remain recognizable for recovery, not a payment verification feature. Printed local cash receipts clearly say when Woo sync remains pending.
- Sync sends the exact signed event ID/payload to the central inbox; the plugin has its own unique ID-to-Woo-order/refund mapping. If a response is lost, retrying the **same** event cannot silently discard a local receipt or create a new order ID. The central service verifies Woo identity, lines, amount, payment state and refund entry before acknowledging; an unresolved conflict blocks later events and requires owner review. Products and public retail prices are never edited from the desktop; private Wholesale defaults remain on the device and only owner/manager can approve a negotiated per-sale price when separately enabled.

**Tests so far:** `tests/desktop-*.test.js` exercise the local ledger, signed events, lost acknowledgements, parent pools, cashier limits, cash-only checkout, local snapshots, read-only pilot gates and isolated central mocks. `tests/browser-desktop.mjs` drives the desktop renderer into a real temporary SQLite ledger with a **fake** central service while Chromium is offline; it tests a local cash sale and subsequent signed sync. `php-parser` checks the uninstalled PHP file's syntax; `php -l` also runs when a PHP CLI is present. These tests do **not** exercise a real Woo installation, the Electron/DPAPI runtime, a Windows installer, printer hardware or concurrent online payments.

## Two distinct, default-OFF approval boundaries

1. **Setup:** a different live-trading service (never the catalogue pilot) requires `POS_DESKTOP_SETUP_APPROVED=true`, a distinct documented setup reference, a dedicated WordPress Application Password and a random 32+ character device master secret. This permits enrollment, read-only bootstrap and owner-controlled allocations **only after separate review**. It does not authorize selling. The WordPress password and master secret stay exclusively on that central service; neither belongs in the Windows installer or this repository.
2. **Selling:** `POS_DESKTOP_RESERVATION_APPROVED=true` and a **different** acceptance reference can enable lease-backed checkout only after Woo/website last-unit and order side effects have been witnessed and accepted. The checked-in trading systemd unit pins **both** desktop flags OFF even if an environment file is changed. The installed read-only pilot rejects enrollment, allocation and sync. An approval string is not evidence that a website checkout/Paystack race has actually passed.

Installing/activating the PHP plugin would create database tables even with its runtime constant off. Do not install it yet. After a separately approved backup, compatibility review and acceptance plan, its separate `MANSU_OFFLINE_RESERVATIONS_ENABLED` constant would still have to be set; that change alone would **not** authorize desktop selling. The draft assumes Woo managed stock on, checkout holds available, transactional InnoDB tables, GHS, and **Woo tax calculation disabled**. Any unmet condition fails closed. This is not a tax-compliance determination; confirm the actual store's saved setting and the adviser's applicable receipt guidance.

## Blockers / recovery before any usable Windows release

1. **Last unit is not proven exclusive.** Checking existing checkout holds and subtracting allocated stock does not prevent a late Paystack confirmation for an older order, an administrator stock adjustment or another plugin from changing Woo stock afterward. Upstream Woo's ordinary stock decrement is not itself a conditional sufficient-stock update. Inspect the *deployed* Woo 11.0.1 configuration, all relevant hooks and pending/paid/failed/cancelled/refunded order effects; design an effective cross-channel control or owner-approved operational hold, then witness a genuine online-vs-offline last-unit experiment **only with separate live authorization**. Leave selling locked until then. A catalogue refresh or a unit test is not acceptance.
2. **Reservation lifecycle is incomplete.** A grant expires after 24 hours to stop *new* local sales, but its already-subtracted public units are **not automatically returned** to the website. Late synced sales and returns must remain reconcilable. A safe owner-reviewed release/renewal protocol, with a fully drained queue, physical stock count, website adjustments and crash/replay tests, is required before allocating real stock. Do not blindly add expired remaining units to Woo.
3. **Recovery is bound to one Windows profile.** The Settings button creates an integrity-checked SQLite snapshot under that user's AppData; it includes the durable queue but **is not a portable/off-site backup**. Sensitive payloads and the signing key require the original DPAPI user keys. Copying the `.db` to another user or replacement PC does not restore access. Develop and rehearse a secure, single-device disaster-recovery procedure (or full protected Windows-profile restore), revoke/retire a lost device before re-enrollment, and verify WordPress **and** central-trading-ledger backups and restores. Do not assume an AppData snapshot proves recovery from a stolen or dead PC.
4. **Actual financial and hardware acceptance is missing.** Inspect real gross price/tax rounding, notifications and third-party hooks, refunds, receipt/invoice requirements, shift/drawer totals, USB scanner/printer and Wi-Fi interruption on the intended Windows PC. The desktop currently shows local sales and sync status; it is not a consolidated website/POS report and does not implement a cash-shift ledger. Verify staff provisioning, offline lease/clock behavior, restore and key rotation with the owner before collecting cash. The clock-rollback guard detects obvious backward jumps but is **not tamper-resistant across restarts or long offline gaps**; choose a trusted Windows account/device policy and witness expiry/recovery behavior rather than treating the wall clock as proof of a reservation. Disabling a server-side approval **cannot remotely stop an already-offline till before its local lease expires** and may also block sync; an emergency stop must physically stop that single computer, retain its ledger, and reconcile every cash receipt with the owner before stock is released. The 41 held physical-source identities and fresh cutover counts remain outside this build.
5. **Real-PC install and signing remain unverified.** `npm run dist:win` builds a Windows x64 NSIS package with `--publish never`. In this sandbox, electron-builder could not download the Windows Electron binary because the release-asset host is inaccessible/certificate verification failed; **no installer was produced here and TLS was not bypassed**. In [CI run 43356320001](https://github.com/iwani1/mansupos/actions/runs/43356320001) at `ad7f869`, the Windows runner explicitly downloaded Electron, checked its bundled `node:sqlite`, built and hashed an **unsigned QA-only** NSIS installer, verified that it was not signed, then **discarded it without uploading or releasing it**. This is packaging evidence, **not** proof that the actual GUI starts, Windows DPAPI decrypts the ledger, a receipt prints, or installation/upgrade/rollback works on the intended PC. Do not call it a usable Windows release until those tests and the blockers above pass. Code signing and a separately approved public GitHub Release are prerequisites to distribution. Automatic updates are disabled by default and are not a workaround for unsynced sales.

### Reproduce code-only checks without a Woo key

```bash
npm ci
npm test
npm run lint
npm run build:live
npm run test:desktop:browser
# On a trusted Windows builder only: first fetch the official Electron binary
node node_modules/electron/install.js
npm run dist:win # unsigned QA only; never publishes
```

The test fixtures fabricate their own catalogue/keys and write only to temporary local directories. They are not a substitute for the owner's written setup and **separate selling** decisions. Any public Release, plugin installation, live order, or change to the read-only pilot requires an explicit subsequent approval.
