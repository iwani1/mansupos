The proposed `mansu-pos-live-trading.service` uses its own account, private env file, code directory, SQLite ledger, backup unit and **localhost-only port 3188**. It imposes live mode, the correct HTTPS origin, loopback and shift accountability **and hard-locks both order/Wholesale write gates** even if the wrong private environment file is copied. `.env.live-trading.example` also starts with those gates **false** and has no keys or passwords. After acceptance, enabling either gate requires a separately reviewed change to the unit and its tests as well as the private configuration; changing the env file alone cannot unlock this template. This is **not** an instruction to create a Read/Write key or enable trading. Port 3188 and all paths must be checked on the actual VPS before installing anything; if occupied, an administrator must choose another free loopback port in both service commands and the eventual proxy route. The pilot's port 3187 is not available.

## Demo-free live build

Run `npm run build:live` in a dedicated live code directory. This builds the UI and excludes copied `public/demo` illustrations from `dist/` while keeping `favicon.svg` and the application. At runtime, a live/staging POS does not expose a demo sign-in API or serve `/demo/*` files, even if a normal build was accidentally copied. Non-demo ledgers never seed demo products, users, stock or example sales; on startup, old **unused sample-stock rows only** are removed from a non-demo ledger. Real users, orders and catalogue cache remain. A ledger containing demo-mode records or belonging to another mode is rejected rather than silently converted. Do **not** delete or restore over the separate demo, pilot or trading SQLite databases.

## Before a supervised first real sale

Follow [LIVE-CASH-ROLLOUT.md](LIVE-CASH-ROLLOUT.md): inspect live order webhooks, Paystack/plugin triggers, emails and fulfilment; verify the actual Woo tax/stock/status behavior and concurrent last-item control; record the reported off-host shop restore; arrange an off-host backup and isolated restore of the **new trading ledger**; verify cash drawer, receipt details, scanner/printer and emergency reconciliation. Get a written owner-approved genuine cash-sale plan. **Preparing an order itself is a live Woo write.** No dummy order, gateway test payment, or globally disabled online checkout is part of this path. If any side effect cannot be controlled, remain read-only.

Only a reviewed administrator should later install the distinct service using a root-owned `0600` copy of `.env.live-trading.example` in `/etc/mansu-pos-live-trading/pos.env`, a separate `mansu-pos-trading` system user and data directory `/var/lib/mansu-pos-live-trading`. Never paste a key or temporary password into chat, Git, shell arguments or browser settings. Preflight fails until the new owner and Woo credentials are configured. With the write gate **false**, `/api/health` may be 200 while `/api/ready` is deliberately **503** (`Live write gate is disabled`); that is not a reason to enable writes early. Confirm localhost binding and that no demo records or assets are served. Back up the new ledger using the separate `mansu-pos-live-trading-backup.service` and test an isolated restore **before** enabling checkout.

After the owner signs off the pending/paid order side effects, tax, shared stock safeguards and rollback/reconciliation plan, a separately reviewed cutover may amend the separate service's write locks and use a dedicated restricted Woo key with necessary order access. The owner supervises the first **genuine** cash sale; count cash and confirm Woo order total/stock/paid state before releasing goods. Wholesale additionally requires its own written decision and documented acceptance-plan reference, and stays locked until verified. Only after both workflows pass may staff access be considered. Nginx can be pointed from the pilot's upstream to the separate trading service **only after** an approved change review and `nginx -t`, without changing the other app's virtual host. Keep old orders and ledgers for reconciliation; never merge, reset or copy the demo/pilot database into trading.

**Emergency (only after a reviewed trading cutover):** Set the trading service write flag false and restart only that service, but preserve its ledger. With writes closed the POS cannot record payment or cancel an existing unpaid order; the owner must reconcile in WooCommerce. Never roll back a POS ledger over newer orders or disable live online Paystack to work around a POS problem.
