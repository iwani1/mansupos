## C. Shared inventory reservation design

**Admission invariant for each eligible managed-stock owner `m`:** `effective_available(m) = current Woo managed _stock(m) − sum(unexpired Woo holds for pending/draft orders on m)`, with admission requiring `effective_available ≥ requested units`. The *stock owner* is Woo's `$product->get_stock_managed_by_id()`, not the option label, SKU alone or each child variation's displayed stock. Two parent-managed variations share the **same parent ID** and hold pool; an independently managed variation uses its own ID. A reservation changes the Woo hold table, not the raw `_stock`; payment makes **one** native Woo reduction and releases that order's hold. This invariant depends on the actual installed DB/hooks/gateway and is an acceptance target, not a current guarantee.

1. **Eligibility:** in the first shared-stock cohort require published, purchasable simple/valid variation, correct parent and exact attributes, managed stock, known positive integer quantity, no backorders and no external plugin overriding the stock owner. Reject untracked/unknown/backorder/composite/bundle/subscription products until each has a separately tested policy. The existing `validateAvailability()` accepts some untracked/allowed-backorder products; the Woo-side bridge must **fail closed** for this narrower cohort. An owner-approved crosswalk and fresh physical recount, not `products.csv` or the old PDF, establish the product and initial Woo stock before a *later* cutover.
2. **Admission/atomic hold:** POS first writes its durable UUID/key/cart/quote/actor/shift intent locally. A proposed `POST /wp-json/mansu-pos/v2/attempts` authenticates the **POS server**, claims `(service_identity, idempotency_key)` in a new InnoDB table (unique key, cart fingerprint, Woo ID), validates exact products and approved quote, constructs one *pending* Woo order via Woo CRUD with the existing `_mansu_pos_key`, channel, cashier and quote metadata, and calls **`wc_reserve_stock_for_order($order)`**. Woo 11.0.1 `ReserveStock` aggregates by stock-owner ID and uses InnoDB locking/conditional insertion into `wc_reserved_stock`; classic and block website checkout already use that mechanism (D). Use a short DB transaction/consistent lock ordering for mapping + Woo order + hold **only if** the approved local Woo fixture proves the DB locking, every involved HPOS/legacy table is InnoDB, and independently inspected installed Woo/plugin hooks do not invalidate that conclusion; otherwise stay blocked. A transaction cannot undo dispatched emails/webhooks or money; a failed insert may still leave a visible pending/cancelled order. If all-or-nothing Woo/order creation is unprovable, **commit the unique attempt claim before any order creation**, persist `create_started`/the Woo ID as soon as known, and use an idempotent *same-order* compensating cancel/release and prohibit cash; never pretend the side effect did not occur. If a crash leaves an attempt claimed but no verifiable Woo mapping, quarantine that key and inspect exact POS metadata/ordered side effects instead of allocating another Woo order. No second Woo order for the same key, fingerprint mismatch `409`, duplicate key after timeout resolves the original mapping or stays in review. The current 15-minute retail same-cart heuristic remains secondary; it is **not** a global cross-cashier uniqueness guarantee.
3. **Confirm rather than infer:** the extension returns Woo ID, immutable key/actor/site identity, exact line products/variation attributes, authoritative GHS gross/tax and hold owner/quantities/expiry from Woo. POS persists the link/hold observation in one local transaction and checks the original quote/total; if the hold did not actually exist on every managed pool, do **not** show “ready for cash.” A read-only status endpoint keyed by the same service/key is the recovery authority; the existing bounded Woo key search is only a legacy fallback, not proof of global absence.
4. **Expiry:** choose a finite POS hold TTL (candidate **10 minutes** for local synthetic fixtures only; owner decides after checkout timing tests). `woocommerce_order_hold_stock_minutes` can be scoped to POS orders **if needed**; leave website's configured hold unchanged. Repeated GET/retries must not renew a hold (core insert-on-duplicate could extend it). Any explicit extension requires a *new* locked capacity check, maximum absolute lifetime and an audit event. The Woo DB clock and hold row are authoritative. A namespaced Action Scheduler job (plus monitored recovery sweep) verifies status/absence of cash finalization, cancels unpaid POS orders and calls `wc_release_stock_for_order`; the core default `wc_cancel_unpaid_orders()` should **not** be assumed to include `created_via=mansu-pos`. Even when the job is late, an expired hold does not count as available protection; the payment endpoint refuses expired/unverified holds. A recorded uncertain cash tender becomes a liability/review, not an implicit paid sale or endless hold.
5. **Payment/late website callback:** before any POS `payment_complete()`, the bridge serializes on the same Woo stock-owner rows and attempt, verifies its live unexpired hold, current order/line/total/actor, and that no other hold/stock adjustment defeats the reduction. It then marks cash payment on **that order once**, verifies Woo's native `_order_stock_reduced` / per-line `_reduced_stock` and observed product quantity/hold release, and returns the same paid result on replay. Never do a separate POS `_stock` update or suppress normal Woo reduction. **Critical:** Woo 11.0.1's ordinary reduction can subtract stock without a fresh nonnegative check if a gateway marks an *expired* website order paid. Inspect the installed Paystack callback/hooks **read-only** and simulate relevant paths on an optional temporary local Woo fixture; a compatible pre-payment/paid-status guard must re-acquire capacity for that *same website order* or stop stock/fulfilment and create an explicit gateway-payment liability. If installed behavior cannot safely be verified, treat this as a production blocker. `woocommerce_pre_payment_complete` is a candidate only if the installed gateway actually calls `WC_Order::payment_complete()`; direct status writes need their own audited interception. If any installed gateway/plugin bypasses this guard, **strict shared last-unit safety is unproved and trading remains locked**. A captured external payment cannot always be prevented by a stock hook; refund/exception handling is separate from stock safety.
6. **Cancellation/refund:** a known unpaid POS order with **no physical tender** may be cancelled once; Woo releases its reservation; repeated cancel is read-only/idempotent. A paid order uses the separately approved refund design (G), not an unpaid-order cancel. A Woo refund does **not** automatically prove a cash payout or returned goods; do not auto-restock. In Woo admin, an unexpected order edit, product-stock adjustment, early checkout hold release or late website payment must raise an alert and require owner reconciliation. If the DB engine, reservation table, HPOS joins, filters, scheduler, plugin callback or payment guard is unavailable, fail closed for POS selling. A stock-availability GET is only a *display hint*.

**Guarantee boundary:** atomic Woo reservation can prevent normal concurrent website/POS *admission* for the same managed pool when both paths truly use compatible Woo holds. It cannot make network payment, emailed notifications, external Paystack capture, physical cash, admin stock edits or untested plugins part of one database transaction. Exercise each bypass on synthetic local fixtures and document the gap to installed-site behavior; do **not** advertise absolute oversell prevention until critical installed checkout/gateway paths can be verified safely. If they cannot, selling remains disabled.

## E. Cash-only checkout state machine and cash-control rule

**States are proposed, not implemented.** Treat Woo status/hold, local sale state and *physical cash custody* as separate facts. Current `sales.status=awaiting_payment/paid/needs_reconciliation`, `sale_events`, prepared totals, quote approvals, shifts and recovery queue are a starting point; they do not prove a hold or a payout.

| State / transition | Required evidence and user action | Stock/order/cash result |
| --- | --- | --- |
| `DRAFT → INTENT_RECORDED` | Authenticated cashier and **open own shift**; select Woo product + exact variation, optional authorized existing customer or walk-in; retail uses current Woo price; Wholesale owner/manager separately approves final per-line **tax-inclusive** quote and optional buyer. Save server-issued UUID/key/cart fingerprint, actor/shift and approval. | No Woo order, hold, tender or receipt. UI never treats a cached stock count as authority. |
| `INTENT_RECORDED → RESERVING/RESERVE_UNKNOWN` | Write `woo.create_started`, then send one server-to-server create/reserve request. If request times out, retain original key and query bridge status; **never POST with a new key**. | Zero or one Woo **pending** order, maybe a live hold; **no cash**, no completed sale. Disable buttons while unknown. |
| `RESERVING → HELD_UNPAID` | Woo returns one mapped ID, verified live hold/expiry, exact lines/variation/stock-owner identity, GHS total/tax and no unauthorized fees/shipping. Wholesale may only perform its controlled reprice of **the same held order** and verify exact agreed gross; mismatch → review/cancel unpaid without cash. | Raw stock unchanged; one time-limited hold; local sale remains unpaid. Only now may cashier prepare to collect cash. |
| `HELD_UNPAID → CASH_IN_CUSTODY` | Check minimum hold time left; if needed request one bounded, capacity-rechecked renewal **before** taking money. Count physical tender and change with customer; durably record cashier, open shift, tendered amount, change actually given and net cash **retained** before initiating Woo payment. If local evidence cannot be written, do not accept cash; if it physically happened anyway, stop and record a manual incident. | This is a **cash liability**, not a paid sale or receipt. Drawer expected balance includes cash physically retained once; block shift close while unresolved. No goods handover. |
| `CASH_IN_CUSTODY → COMMITTING` | Save one payment intent and use the **same** Woo ID/key and bridge `cash/commit` under active stock-owner locks; payment reference is a server-side POS cash marker, not Paystack. Never resubmit with a different amount/actor. | Unknown response remains `REVIEW_REQUIRED` with custody tracked; do not take more cash, issue paid receipt or release goods. |
| `COMMITTING → PAID_VERIFIED → RECEIPT_ISSUED` | Re-read Woo paid status/date, matching POS cash marker/order/quote/hold, native stock reduced exactly once, hold released, retained cash and local audit committed. Generate one immutable numbered POS receipt with Woo number, GHS gross/tax as returned, cashier, shift, tender/change and approved Wholesale attribution; hand over goods only after verification. | Exactly **one paid Woo order per completed POS sale**, stock deducted once, one net cash collection in current shift; website Paystack ledger unaffected. If receipt printing fails, reprint the *same* receipt, not another sale. |
| `HELD_UNPAID → EXPIRED/CANCELLED` | Expiry/cancel applies only while **no tender was accepted**. Confirm Woo cancelled/hold released, or leave in review if the response is uncertain. | No POS cash/paid receipt; raw stock unchanged. An expired key is closed, not silently renewed into another sale. |
| `CASH_IN_CUSTODY/COMMITTING → REVIEW_REQUIRED` | Woo unavailable, hold expired, late callback, changed total, mismatch, payment timeout or local commit failure. Owner/manager review same mapped Woo order, WP attempt, POS event trail, drawer and notification/fulfilment state. | No automatic paid receipt/goods release. If Woo already paid with intact evidence, finalize local receipt **once**; if definitely unpaid and stock unavailable, return the retained cash using a separately authorized, documented **unapplied-tender reversal** in the paying shift (distinct from a refund of a completed sale). If disputed, retain cash liability and do not close shift or backdate cash. |

**Physical cash rule:** if the cashier has GHS 100 and gives GHS 20 change against an GHS 80 sale, exactly GHS 80 is retained in the drawer. If Woo confirmation fails, GHS 80 is *cash in custody / amount owed*, not revenue and not a completed receipt. The current Phase 1 `payment.intent` alone does **not** establish that cash was physically collected; Phase 2 must add a distinct custody record and counted/returned evidence. A remote paid status without that record is not proof of cash. A genuine cash return when the Woo order never paid is a documented liability discharge, **not** a Woo cash-sale refund; owner must approve both procedures before implementation. Do not use the current generic cash-out button to disguise either transaction.

Customer selection must be optional unless the owner decides otherwise: walk-in has no fabricated Woo customer, an existing named customer is looked up only with permission/consent, and receipts/metadata store minimum necessary data. Wholesale remains **owner/manager-approved**, not a cashier-chosen public price. ## G. Proposed cash-refund workflow — policy approval still outstanding

The Phase 1 review's owner-decision draft is the basis, **not authorization**. Propose a distinct cash-refund state machine for an **already Woo/POS-paid cash sale**:

1. **Request:** link original POS sale UUID, Woo order ID, original cashier/shift, amount originally *actually* collected in cash, reason, customer acknowledgment where appropriate and optional return lines. Cashier may request but cannot approve; a manager/owner verifies the original sale and remaining refundable balance. A website Paystack/MoMo/card refund must not be paid from the POS drawer.
2. **Approve a partial/full refund:** owner/manager not equal to the payer except an explicitly approved emergency exception. For a *new* Woo refund, cap the proposed amount at both `original net cash collected − cash refunds already approved/paid` and Woo's **remaining refundable amount before creating that refund**, checked under the appropriate POS and Woo-side serialization. Once a Woo refund ID exists, its remaining Woo-refundable balance will have fallen; do **not** reapply that balance as a cap on paying the *already-authorized* refund. Instead enforce `cash paid against this refund ID ≤ approved matched Woo refund amount` and `cumulative cash paid/approved ≤ original net cash collected`, reconciling other/external refunds before each approval/payout. For a POS cash refund, create an idempotent Woo refund record with **`refund_payment=false` and `restock_items=false`**—never call a Paystack/card refund or presume cash left the drawer. One Woo refund record/ID per approved portion by default; `UNIQUE(woo_order_id, woo_refund_id)` and `UNIQUE(idempotency_key)`, with cumulative quantity/amount checks prevent second payouts or over-refunds. If a Woo refund was created externally, record it as **observed / unpaid liability** until matched and explicitly authorized; do not create another refund blindly. No payment can be inferred from Woo refund status.
3. **Evidence and actual payout:** separately identify approving user, cashier who *physically* pays, witness (if required), original and paying shift, amount, date/time, method `cash`, customer receipt/signature or minimally retained equivalent, and evidence attachment digest in private storage. Atomic local payout + one append-only event + exact drawer deduction in the **open paying shift**; block duplicate/disputed payouts. If the original shift is closed, keep its historic counted/expected/net snapshot unchanged. A pending approval with no physical payout remains a visible **unpaid refund liability**; if cash leaves but Woo is missing/refund failed, record an unresolved discrepancy, not a fictitious successful Woo refund. The Phase 1 generic `cash_movements` button is not this authorization flow.
4. **Goods/stock:** separately inspect returned item IDs/variation, quantity, condition and acceptance; choose restock/quarantine/repair/write-off/no-return. Default Woo refund `restock_items=false`. Only an independently approved restock action uses Woo's original reduced-stock/return mechanism once per Woo line/qty; track cumulative restocked quantity across partial refunds, website returns and POS returns. Cash payout is **not** automatic stock return; Woo stock return is **not** payout proof.
5. **Reconcile/reverse incident:** compare Woo refund ID/amount/order status, POS payout, paying shift, customer evidence and stock actions. A disappearing/changed Woo refund raises review without erasing observations. A payout after shift close belongs to the *later paying shift*; never edit/backdate the original shift. A physical return of **unapplied tender before a paid sale exists** is a different custody-reversal procedure (E), not a Woo sale refund.

**Explicit owner decisions before implementation:** who can approve vs physically pay, whether a witness/customer signature and what retention are required, permitted refund window/reasons, whether multiple cash installments against one Woo refund ID are allowed (default proposal **no**), how split tender or a payout with no open shift works (default **stop and escalate**), tax/credit-note obligations, who authorizes restock and when unsellable goods are quarantined, and whether an owner may exceptionally perform both approval and payout. Until these are approved, there is **no** refund API, payout record or altered shift formula in the application.
