## Phase 3.0 — Synthetic-only pinned Woo/Paystack read contract (2026-11-15)

**Scope and release status:** `server/readonly-evidence-source.js` introduces a **synthetic-only HTTP read adapter**, exercised exclusively with injected fake HTTP responses in `tests/readonly-evidence-source.test.js`. It is **not called from `server/app.js`**, has no browser/API endpoint, is not on a production scheduler, and does not read the actual Mansutrendzgh website or merchant Paystack. Constructor refusal requires `NODE_ENV=test`, an additional synthetic-test flag, a fixed `.invalid` Woo origin, exact synthetic credential markers and an explicitly injected fake HTTP client distinct from native `fetch`. No real credentials may satisfy that contract; no production environment variable enables it.

**Bounded GET-only contract:** a future credential-isolated backend could request a single original Woo `/wc/v3/orders/:id`, its Woo refund index `/wc/v3/orders/:id/refunds?page=1&per_page=100`, and the read-only Paystack `/transaction/verify/:reference` with pinned origins, request timeouts, `redirect:error`, no redirects or arbitrary URLs, strict JSON status/content and response size bounds. There are **zero POST, PUT, DELETE, webhook, refund, stock or payout methods**. Its synthetic fake HTTP client proves only the request contract, not the actual site permissions or provider compatibility.

**Original payment and refund identity:** it validates the Woo order ID, GHS currency, Paystack method, positive exact two-decimal order totals, one original `_paystack_txn_ref` value, unique Woo refund IDs and an exactly complete refund page with `X-WP-Total` and `X-WP-TotalPages`. It reconciles positive or Woo-signed-negative refund amounts, refuses duplicate, omitted or oversized/multipage refund history and forbids cumulative Woo refund totals larger than the original order. It reads the same original Woo order **again** after the synthetic gateway verification, refusing a changed status, amount, reference, modification marker or refund index. It requires the synthetic Paystack verify response to contain an explicit transaction ID, amount, currency, reference and status; discrepancies are passed to the offline `compareSettlementEvidence` diagnostics, not treated as proof of payment. Raw reference IDs, secrets and customer identities are never returned.

**Fail-closed reporting:** synthetic reads may confirm only that *two mock APIs provided matching or mismatching values*. Their response explicitly says `disconnectedFromMerchant:true`, `merchantSourceAuthenticated:false`, `websiteOrdersGloballyScanned:false`, `gatewayRefundHistoryComplete:false`, `independentSettlementAvailable:false`, `financialOperationsEnabled:false`. The underlying comparator always keeps `authOfSourcesVerified:false`, `merchantOwnershipVerified:false`, `bankFundsReceivedVerified:false`, `gatewaySettlementVerified:false`, `payoutToCustomerVerified:false`, `refundAuthorized:false`, `refundExecuted:false`, `stockRestorationAuthorized:false`, `checkoutAuthorized:false` and `writesAllowed:false`. A Woo refund record does not confirm the payment processor or bank sent money back to the customer. A Paystack verification success does not confirm actual bank credit.

**Tests and remaining work:** the synthetic tests check fixed origins and credentials, fake GET-only execution, no retries or writes, unchanged order snapshots, incomplete/duplicated/over-refunded Woo evidence, wrong gateway references or amounts, and zero disclosure of customer/payment data in results. **Actual authorization** still requires a separately provisioned *read-only original-order Woo credential* (not the existing catalogue-only pilot credential), a merchant-authorized Paystack verification credential, a confirmed merchant/site identity and installed-plugin/HPOS survey, a separate trustworthy settlement and refund-payout record, and explicit go-live acceptance. Do **not** copy these synthetic credentials into an environment, contact the merchant or turn on checkout. `lateGatewayGuardVerified: false` remains in place.

## Phase 2.9 — Post-lock Woo order-state freshness and offline evidence comparator (2026-11-15)

**Why this build was prioritized:** Disposable Woo/Paystack run [43721775378](https://github.com/iwani1/mansupos/actions/runs/43721775378) exposed a real intermittent **two-worker Paystack webhook/return race**. Both workers verified the same transaction, one deducted physical stock and set a paid date, while the other wrote a stale `on-hold`/Owner-review marker and a second gateway success note. This contradicted the once-only callback claim. **Do not treat the earlier Phase 2.8 conformance as passing.**

**Fix, draft Woo bridge only:** After the request has acquired its per-order MySQL advisory lock and revalidated the original Paystack reference, it reads the order's **canonical current database status from the same locked MySQL connection**, selecting the Woo HPOS `wc_orders.status` or legacy CPT `posts.post_status` store explicitly. The earlier `wc_get_order()` snapshot may have been cached before the lock, so it is not sufficient to decide whether the gateway should execute again. Only a still-pending order reaches upstream Paystack verification. Already processing, completed, refunded or on-hold orders short-circuit before the second gateway verification/success note; canceled, failed, draft and unknown statuses fail closed, not as newly payable orders. For a return URL that encounters an already processed order, Woo's canonical order receipt URL is used instead of processing again. MySQL `RELEASE_LOCK` is registered **immediately after successful GET_LOCK**, so a short-circuit/early exit cannot strand a persistent connection's advisory lock. The lock-loss pre-payment and stock-reducer protections from Phase 2.6 remain active.

**Regression acceptance:** In [green pinned Woo 11.0.1 / Paystack 5.8.6 disposable run 43723072385](https://github.com/iwani1/mansupos/actions/runs/43723072385), both PHP workers entered each racing endpoint, but **only one entered external gateway verification**. The valid race completed **`processing`, original paid date present, exactly one stock deduction and gateway success note, no review marker**. The expired-hold race ended **`on-hold`, required review, zero item-level deduction**, with one verification. The same run passed 66 Woo-core assertions, 23 upstream Paystack method assertions, DB disconnect and replay quarantine, 20-second advisory lock timeout/retry, 40 synthetic HTTP callback assertions and six independent last-stock-unit Woo/MySQL races. No real Paystack account, website, order or Contabo deployment was touched. The test is not proof of safety against out-of-band Woo order writers, pooled/persistent DB peculiarities, different HPOS settings, network partitions, live payment settlement or installed-plugin compatibility. The release flag stays false.

**New pure source-comparison module (no API endpoint):** `server/settlement-evidence-comparison.js` implements `compareSettlementEvidence()` against **caller-supplied, untrusted normalized snapshots** of the original Woo order, a synthetic Paystack verification, a synthetic settlement batch, cumulative refund entries, and other original Woo reference claims. It detects attempt/reference mismatches, the same reference claimed by multiple Woo orders, different currencies or amounts, failed/pending transaction and settlement states, gateway refund IDs/references used twice, partially processed refunds, refund totals exceeding original payment, and settlement gross/fee/net disagreements. The report never returns raw gateway transaction IDs/references. Its flags **always** state `authOfSourcesVerified:false`, `merchantOwnershipVerified:false`, `bankFundsReceivedVerified:false`, `gatewaySettlementVerified:false`, `payoutToCustomerVerified:false`, `refundAuthorized:false`, `refundExecuted:false`, `stockRestorationAuthorized:false`, `checkoutAuthorized:false`, and `writesAllowed:false` even if arithmetic matches perfectly. It performs **no live Woo, Paystack, bank, refund, stock or POS calls** and does not persist provided data. `tests/settlement-evidence-comparison.test.js` checks source mismatch/duplicate/refund/balance cases and these hard-closed claims.

**Still required:** independent authorized read-only access to the **actually installed** Woo/Paystack settings and original transaction/settlement records, a trusted source-authentication protocol, bank-payout proof, merchant identity binding, original customer refund recipient verification, real partial/final refund accounting and Owner approvals, physical return inspection, valid Woo stock-owner restoration, restore/incident drills and final approval. The pure comparator **does not make a source authentic** and is not exposed as a "verified funds" UI. `lateGatewayGuardVerified: false`, draft PR, no merge/installation/deployment.

## Phase 2.8 — Draft refund resolution dossier and two-person review (2026-11-15)

**Purpose:** The new `server/refund-resolution-dossier.js` distinguishes a *proposed remedy*, a *different Owner's review of the draft*, *verified customer payout*, *physically inspected garment return* and *approved Woo stock-owner restoration*. Only the first two are recordable, and **only in isolated tests**. The last three remain unverified and unactionable. This is **not a live refund authorization engine**.

**Owner/Manager read-only API:** `GET /api/payments/reconciliation/:saleId/resolution` returns the original POS sale, cumulative locally observed Woo refund, proposal/review history, contradictions and independent evidence requirements. The Payment Reconciliation screen displays a **Resolution decision dossier** accessible without a financial write. The server and UI maintain `settlementVerified:false`, `payoutVerified:false`, `returnPhysicallyInspected:false`, `ownerRefundApprovalIssued:false`, `cashPayoutAuthorized:false`, `refundExecuted:false`, `wooStockRestorationAuthorized:false`, `stockRestored:false`, `goodsReleaseAuthorized:false`, `checkoutAuthorized:false`, `mutationsAllowed:false`, and `decision:external_evidence_and_authorization_required`. This is a local POS ledger source, **not** a Paystack/bank or website order feed.

**Isolated test-only writes:** POST `/api/payments/reconciliation/:saleId/resolution` records a fixed-code, non-executing remedy draft: `refund_only`, `return_and_refund`, `exchange_request`, or `no_refund_review`. Refund draft amounts are positive whole pesewas within the locally observed remaining order total; non-refund drafts carry zero payout. This is an **arithmetic constraint, never permission to pay**. A strict payload rejects free-text PII, references or arbitrary evidence. Snapshot status, updated timestamp, original Woo ID and cumulative refund must still match the original POS sale. Exactly one draft is allowed per sale; UUID-based retries are idempotent and a reused key for another case is rejected. App-controlled append-only `sale_events` and audit entries are written in one SQLite `BEGIN IMMEDIATE` transaction.

**Independent Owner review:** POST `/api/payments/reconciliation/:saleId/resolution/owner-review` can record a *review acknowledgement* only from an Owner different from the original draft author, after rechecking the original order and cumulative refund. It **does not approve the refund**. No Paystack transaction, WooCommerce order, cash drawer, customer payment, receipt, physical return, inventory quantity, refund status or closed shift is modified.

**Release gate:** Both POST routes require `POS_MODE=demo`, `NODE_ENV=test`, no production flag and no read-only profile; **live, staging, and Contabo pilots always receive HTTP 403**. GET requires Owner/Manager; Cashier and unauthenticated users are denied. No Woo order-read credentials or live payout data are requested. The `lateGatewayGuardVerified: false` interlock is unchanged.

**Acceptance tests:** `tests/refund-resolution-dossier.test.js` covers two-person review, idempotency, sale/UUID mismatch, over-refunds, full prior refunds, order/refund snapshot changes, no PII fields, and blocked live writes with unchanged money/stock rows. `tests/browser-live-pilot.mjs` mocks the GET-only dossier and forbids payment-action buttons. Installed Woo compatibility, actual settlement, independent payout proof, return inspection, customer eligibility, Owner release approval, partial refund disbursement and single-authority Woo stock restoration remain separate required builds and independent acceptance gates.

## Phase 2.7 — Read-only partial/full refund evidence policy (2026-11-15)

**Implementation:** `server/refund-evidence-policy.js` adds a pure, non-executing policy evaluator, exposed as Owner/Manager-only `GET /api/payments/reconciliation/:saleId/refund-evidence` with an optional positive integer `proposedCents` (max GH₵1,000,000). The payment dashboard now displays an **optional hypothetical GHS refund amount**, original POS order total, cumulative locally observed WooCommerce refund amount, remaining arithmetic difference, and a required verification checklist. All amounts are integer pesewas internally. This GET is safe on the live read-only catalogue pilot; it does not require new Woo credentials, Woo order reads or a payment processor connection. There is **no POST endpoint** for a refund proposal, payout, bank settlement, stock return or inventory movement.

**Partial/full refund controls:** the policy distinguishes no recorded refund from a partial or full **Woo refund observation** and calculates `originalTotal - cumulativeRecordedRefund` only if both totals are valid. A proposed amount exceeding that remaining observed balance is explicitly rejected as a mathematical mismatch; a proposal exactly matching it yields a hypothetical zero difference, **not payment authorization**. Over-refunded orders, missing original Woo identity, missing original POS payment verification and inconsistent paid/refunded statuses produce visible warnings. The amount limit is an anti-abuse bound for a read-only worksheet, **not a permitted refund limit**.

**Evidence barriers:** every case includes independent customer entitlement/recipient verification, settlement and prior-payout checks, separate refund approval and disbursement confirmation, physical receipt/inspection of any garments to be returned, and a separate Woo-managed stock-restoration decision. Even when some local POS evidence exists, **none** of external settlement, physical cash payout, customer entitlement, garment return, item condition or restoration permission is marked verified by the system. A Woo refund row is not proof that a cashier physically returned cash; a POS cash-intent event is not custody and neither POS nor Woo marked-paid status proves bank settlement.

**Hard response interlocks:** `kind: read-only-refund-evidence-policy`, `source: local-pos-ledger`, `websiteOrdersIncluded: false`, `auditOnly: true`, `mutationsAllowed: false`, `checkoutAuthorized: false`, `refundAuthorized: false`, `refundExecuted: false`, `cashPayoutVerified: false`, `gatewaySettlementVerified: false`, `stockRestored: false`, `returnInspected: false`, `fulfilmentAuthorized: false`, `decision: manual_review_only`. The browser refuses any response without these exact safety properties. Owner/Manager may view the worksheet; Cashier and unauthenticated users are denied by the server. No additional migrations or payment credentials.

**Acceptance tests:** `tests/refund-evidence-policy.test.js` covers cumulative partial and prior full refunds, exact-remaining and over-limit hypothetical requests, invalid original/refund totals, missing POS verification and original Woo ID, invalid request values, role access, and proof that observing the policy does not mutate the POS ledger or call a Woo order API. `tests/browser-live-pilot.mjs` performs an isolated mocked browser read of the partial-refund worksheet to ensure no financial write calls. It is **not** an installed Woo/Paystack live settlement or payout test.

**Still blocked:** documenting and actually verifying the correct original payment beneficiary, real merchant gateway/bank settlement, partial cash payouts and physical cash custody, independent Owner release approval, returned item condition/size and single-authority Woo stock-owner restoration. Only after those have their own installed-site tests, incident/rollback procedures and explicit business approval may any *separate* refund execution design be considered. `lateGatewayGuardVerified: false` stays unchanged.

**Separation of duties:** an authenticated Owner or Manager can record a *predefined investigation request* against an existing exception; **only a different Owner account** may acknowledge that request. **Data and correctness:** requests select one of four fixed actions: verify the original Woo order; reconcile the original POS cash drawer; request *evidence* for a cash-refund payout already recorded in Woo; or escalate an unresolved financial exception. **What remains:** an independently accepted policy for verifying external settlement, evidence and who may physically return cash, exchange items and restock returned garments, including partial payouts and closed-shift treatment. This milestone does **not** close exception cases or prove website Paystack reconciliation.

## Native Woo late-website-payment guard prototype — still NOT live accepted

The earlier pinned WooCommerce 11.0.1/MySQL test **reproduced** a real native order oversell: a website order's hold expired, POS sold the last unit, and a late website `payment_complete()` deducted stock from 0 to **−1**. This was a deliberately synthetic local test, not a store incident.

The uninstalled Woo bridge now includes a **fail-closed native Woo hook prototype** for checkout-created website orders while the bridge is enabled:

- `woocommerce_pre_payment_complete` verifies the website order's original Woo stock-owner holds and at least 30 seconds of remaining validity. When absent/expired, it refuses native payment completion, adds an order note and a `_mansu_website_stock_review=required` marker, and moves the disputed order to **on-hold**. This prevents the tested Paystack webhook from repeatedly generating success notes for a pending order. No gateway money is automatically voided or refunded; Owner/Manager reconciliation is mandatory.
- `woocommerce_can_reduce_order_stock` rejects an unverified website order's stock reduction, including Woo's direct status-transition stock hook.
- `woocommerce_order_status_changed` moves unverified *direct* processing/completed transitions to **on-hold** review. It checks per-line `_reduced_stock` evidence instead of blindly trusting Woo's order-level `stock_reduced` flag: Woo core may set that order-level flag even when a plugin denies physical item reductions.
- A **request-local**, never persisted payment-complete hold check prevents a properly held website order from being falsely quarantined after Woo's own payment pipeline releases the reservation.

The ephemeral real Woo/MySQL test exercises an ordinary held website payment, both opposite orderings of expired website callback vs POS payment, and a direct paid-status bypass. It verifies the expired website order requires review and stock never falls below zero **for these exact native Woo hooks**. It also preserves six independent two-process last-unit Woo/MySQL races. CI prints `DISPOSABLE_WOO_LATE_WEBSITE_GUARD_OK` when this limited exercise passes.

**This is not a payment capture guarantee or live Paystack acceptance.** A gateway may update order status, modify `_stock`, acknowledge funds or trigger notifications through other paths; verification against the actual installed Paystack version and any checkout/stock plugins is required. There is no cross-system atomic settlement guarantee and no automatically approved refunds or physical cash disbursements. The genuine live readiness attestation remains deliberately **false**, no Woo plugin is installed on the website, and the existing read-only POS remains unchanged. Operators must not ship goods from a quarantined website order without manual payment, stock and refund reconciliation.

## Additional quarantine and actual Paystack gateway conformance (draft, not live)

- **Sticky quarantine:** once an order receives `_mansu_website_stock_review=required`, rebuilding a valid Woo hold later must never automatically authorize that already-disputed website payment. A real pinned Woo/MySQL regression deliberately resets a quarantined order from on-hold to pending and attempts a new Woo reservation; the order still cannot complete or reduce stock. A new order/refund cannot be inferred from a renewed hold.
- **Short payment on-hold:** successful but underpaid Paystack transactions can change status directly to `on-hold`, skipping `payment_complete()` and any explicit stock reducer. The draft guard now attaches Owner/Manager review evidence when a Paystack-style website order moves to `on-hold` without a valid original reservation, while preserving the on-hold state. This also covers direct expired-hold admin on-hold transitions; it does not prove the funds received.
- **Real plugin method, fake payments:** the disposable GitHub Actions workflow installs the publicly released **Paystack for WooCommerce v5.8.6** alongside Woo 11.0.1, then invokes its actual `WC_Gateway_Paystack::process_token_payment()` method against synthetic products and a `pre_http_request` stub. It tests classic and Store API valid payments, delayed last-unit payment, short-paid on-hold, and wrong-currency direct stock-reduction behavior. Paystack API traffic is intercepted locally; no real Paystack customer, credential, settlement or refund is involved. This method-level suite covers only the token/saved-authorization route. Separate synthetic HTTP tests below cover some actual webhook/redirect paths; **normal popup, automated refunds, subscriptions, real settlement, and installed-site plugin/settings paths are NOT accepted.** See `tests/woocommerce-real-paystack-conformance.php`.
- **Paystack wrong-currency oversell reproduced and prevented in the tested code:** the first real-plugin CI exercise drove one synthetic last-unit product from quantity **0 to −1** after the gateway called `wc_reduce_stock_levels()` following an `on-hold` transition. Root cause: Woo can mark its **order-level** `stock_reduced` flag even after item reductions were denied; trusting that flag to bypass the hold guard was unsafe. The draft Woo filter now checks actual line-item `_reduced_stock` evidence and refuses to bypass a review marker. The regression uses both the real Paystack token method and the equivalent direct Woo on-hold/reducer sequence. A passing follow-up disposable run at code commit `46821aa` recorded **66 native Woo assertions, 23 real Paystack method assertions and 6 concurrent last-item races**: https://github.com/iwani1/mansupos/actions/runs/43643461379 . These do not establish production Paystack webhook safety or financial settlement atomicity.
- **Known release blocker:** upstream `process_token_payment()` returns a successful method result even when Woo `payment_complete()` returns false after a stock-safety quarantine. Thus a positive Paystack gateway return value cannot be treated as proof that a Woo order was paid/stocked/fulfillable. Manual financial reconciliation is mandatory; no automatic resubmission or cash refund is authorized. The hard interlock `lateGatewayGuardVerified: false` remains unchanged.

### Reproduced cross-worker Paystack race and draft mitigation

Before introducing a callback-level lock, a real isolated two-worker webhook + return race on one *validly reserved* website order ended with **paid date present, stock reduced once, two Paystack success notes, and status on-hold with a false stock-review marker**. The failure was observable at the native Paystack HTTP endpoints, not inferred from a mocked Woo function. A single-process or sequential replay would not have exposed it.

The draft bridge now takes a **per-order MySQL `GET_LOCK` advisory lock** at priority 0 for the known Paystack WC-API webhook and return routes, before the upstream plugin loads the WC order. The lock holds through the gateway handler and is explicitly released at PHP shutdown. If it cannot be acquired within 20 seconds, the callback exits with HTTP 503 **without allowing the stale upstream handler to mutate the order**; webhook retries/owner reconciliation remain necessary. It does **not** capture or refund money, and the live readiness flag remains false.

The test harness now uses **two independent loopback PHP servers sharing a single disposable WordPress/MySQL installation**, with a deterministic entry barrier *before* the order lock and verifier markers from both workers. At [successful run 43649031269](https://github.com/iwani1/mansupos/actions/runs/43649031269), both callback races reached both workers:

DB connection-loss behavior, additional gateways, HPOS, partial refunds and notifications remain unaccepted. **Never deploy this prototype as a payment-readiness guarantee.**

### MySQL callback connection-loss quarantine — disposable CI PASS (2026-11-15)

The bridge's per-order Paystack callback lock is a **connection-scoped MySQL advisory lock**. If WordPress loses/replaces its MySQL session after `GET_LOCK()` but before Woo `payment_complete()`, the lock can disappear even though PHP still has a stale order snapshot. Another worker could then process the same website order concurrently. Previously, the bridge rechecked only the reference and original Woo hold and could accept that stale callback.

Draft bridge code now marks, for this PHP request only, which order entered a serialized Paystack WC-API route; **before payment completion and before native stock reduction**, it checks that `IS_USED_LOCK('mansu-paystack-order-<id>') = CONNECTION_ID()`. If a callback has lost ownership, it fails closed, records sticky Owner/Manager stock-and-settlement review evidence, changes the original Woo order to `on-hold` and prevents a stock decrement. This check does not grant payment authorization; direct Woo hooks and other gateways retain their existing hold/reducer rules, and there is no automatic settlement/refund.

The CI-only MU plugin `tests/fixtures/mansu-ci-paystack-http-mock.php` was extended with an isolated **`connection-reset`** Paystack verification case. During a *genuine signed Paystack WC-API HTTP webhook*, after lock acquisition and before the actual gateway calls Woo `payment_complete()`, it closes the disposable WordPress mysqli connection using `$wpdb->close()` and explicitly reconnects with `$wpdb->db_connect(false)`. A machine-readable local evidence marker demonstrates that both the connection ID changed and the advisory-lock owner changed from **held by current connection (1) to not held (0)**. This mock is never installed on a merchant site.

[Green disposable conformance run 43715498841](https://github.com/iwani1/mansupos/actions/runs/43715498841), at commit `6d36f7bb`, passed **5 assertions** on the initial lost-lock callback and **5 more** on its repeated signed webhook. The original order remained **`on-hold`, review required, unpaid in Woo, stock at 1, no item-level decrement**, with **exactly one Paystack success note** even after the repeat. The same run passed the existing simple/shared-parent POS-vs-website races, 20-second MySQL lock timeout/healthy retry, **40 signed HTTP Paystack assertions**, **66 real Woo assertions**, **23 upstream Paystack-method assertions**, and **six independent two-process reservation races**.

**Residual risk and limitations:** successful transaction verification inside the mocked Paystack response represents **synthetic external payment evidence**, not actual settlement or guaranteed availability of funds. The test exercises a controlled local *disconnect followed by successful reconnect*, not a prolonged database outage, abrupt MySQL crash, lock loss after `payment_complete()`, live gateway callbacks, clustered/pooled DB configuration, or real notification/refund side effects. These remain independent release blockers. A real externally settled-but-quarantined payment requires Owner/Manager reconciliation; never automatically retry Woo payment completion, issue a cash refund, or fulfil the order from a Paystack success note alone. `lateGatewayGuardVerified: false` remains unchanged.

The upstream Paystack v5.8.6 return handler derives a Woo order ID from the verified payment reference without independently comparing it to the order's saved `_paystack_txn_ref` on that path. ## Explicit live checkout safety interlock

The uninstalled Woo online bridge now reports `lateGatewayGuardVerified: false` in its **signed, read-only health response**. The bridge client requires this field, and the live `OnlineSalesService.assertLiveBridgeReady()` refuses to prepare a new Woo order or report collectible cash unless it is **true**. The existing Woo bridge source cannot currently assert it: the native Woo hook prototype is not independently verified against the installed Paystack gateway and cannot cover every callback/stock mutation path. This ensures that copying old live approvals and Woo settings is not enough to activate live transactions. Synthetic tests may inject `true` into a fake bridge **only to exercise other logic**; that fake is not a production configuration and does not affect Contabo.

This is a **deliberate hard blocker**, not a promise that the late callback is safe. It must be lifted only by a separately reviewed, proved Woo/Paystack integration that prevents post-expiry paid orders from silently claiming the same last item, while preserving genuine customer payment and manual refund/recovery evidence.
