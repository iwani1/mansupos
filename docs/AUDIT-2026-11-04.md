**Not ready for live trading.** The isolated demo is safe to explore, and the core UI/build/test baseline is healthy, but the audit confirmed checkout, reconciliation, accounting, restore, and deployment defects that must be fixed and re-tested before enabling live WooCommerce writes.

**Release blockers:** F-01 through F-06, plus the existing staging/hardware/owner-approval gates in `docs/ACCEPTANCE.md`.

## Findings

### F-01 — Critical — Lost prepare response can create duplicate WooCommerce orders

**Status:** Confirmed by browser probe and backend probe.

**Evidence:**

- `src/Register.jsx:39` resets `checkoutKey` when cart/note changes.
- `src/Register.jsx:108` resets `checkoutKey` on any error except `RECONCILIATION_REQUIRED`, including network failure.
- `server/sales.js:64-103` idempotency is keyed only by the client-supplied `idempotencyKey`.

**Reproduction:**

1. Add an item and click Charge.
2. Let the server commit `/api/sales/prepare`, then drop the response.
3. Click Charge again.

Browser probe result:

```text
firstPrepareStatus: 201
errorAfterLostResponse: "Failed to fetch"
awaitingPaymentCount: 2
```

Backend probe with a new key after a lost response:

```text
first: 201
second: 201
remoteOrdersCreated: 2
differentSaleIds: true
```

Same-key retry is safe:

```text
sameId: true
```

**Impact:** In staging/live, a normal network interruption can create two WooCommerce orders for one cart. If both are paid, stock can be reduced twice and the customer may be charged twice.

**Remediation:**

- Persist the checkout key with the cart until a sale is definitively resolved.
- On network/5xx prepare failure, do **not** generate a new key automatically.
- Show “Check Sales / reconcile before retrying” and attempt recovery using the same key.
- Add a server-side recovery lookup by cashier + cart fingerprint + short time window if the key is lost.
- Add automated tests for lost prepare response, lost payment response, and retry after refresh.

**Verification required:** Lost-response test must produce exactly one Woo order and one POS sale.

### F-02 — High — Payment can be recorded against a stale total after WooCommerce total drift

**Status:** Confirmed.

**Evidence:**

- `server/sales.js:115` validates tendered against `row.total` from prepare.
- `server/sales.js:149` saves the remote order after payment.
- `server/sales.js:46-58` overwrites local total/items with the remote response.

**Reproduction:** Fake Woo returns `115.00` at prepare and `200.00` at pay.

```text
paid=paid
total=20000
tendered=11500
change=0
```

**Impact:** The POS can mark a sale paid even though the authoritative Woo total increased after prepare. Cash received/change and ledger totals become wrong.

**Remediation:**

- After `updateOrder`, compare returned total/currency/items with the prepared sale before marking paid.
- If total increased, block completion and require owner reconciliation / additional collection.
- If total decreased, record the authoritative total and recalculate change only with explicit confirmation.
- Store prepared total and final total separately for audit.

**Verification required:** Total-drift test must not silently record `paid` with insufficient tendered amount.

### F-03 — High — Currency drift after prepare is accepted as GHS

**Status:** Confirmed.

**Evidence:**

- `server/sales.js:91-94` checks currency only during prepare.
- `server/sales.js:149` saves the payment response without rechecking currency.
- `src/api.js:9` formats all amounts as GHS.

**Reproduction:** Fake Woo returns GHS at prepare and USD at pay.

```text
paid=paid
currency=USD
total=11500
```

**Impact:** A non-GHS order can be displayed and reported as GHS, producing incorrect financial records.

**Remediation:**

- Enforce `order.currency === 'GHS'` in `saveRemote` or immediately after every remote write.
- Move the sale to `needs_reconciliation` if currency changes.
- Add a regression test for currency drift at pay/reconcile.

**Verification required:** Non-GHS remote response must never become a paid GHS ledger entry.

### F-04 — High — Uncertain cancellation can leave a cancelled remote order payable locally

**Status:** Confirmed.

**Evidence:**

- `server/sales.js:190-200` updates the remote order first, then local status.
- If the remote cancel succeeds but the response times out, local status remains `awaiting_payment`.
- `complete()` does not re-fetch remote status before accepting payment.

**Reproduction:** Fake Woo cancels successfully, then throws an uncertain timeout.

```text
cancel=502
localAfterCancel=awaiting_payment
payAfterCancel=paid
remoteCancels=1
```

**Impact:** Staff can record payment against an order that WooCommerce has already cancelled.

**Remediation:**

- On uncertain cancel, mark the sale `needs_reconciliation` and block pay.
- Before pay, re-fetch the Woo order and reject cancelled/trashed/failed orders.
- Make cancel reconciliation idempotent and visible in Sales.

**Verification required:** After an uncertain cancel, pay must be blocked until reconciliation confirms the order is still payable.

### F-05 — High — Restore safety copy omits WAL and can lose committed post-backup data

**Status:** Confirmed in an isolated WAL probe.

**Evidence:**

- `server/restore.js:22-26` copies only the main `.db` file as the safety backup.
- `server/restore.js:28-31` deletes `-wal` and `-shm` before copying the restore source.
- The runbook says to stop the service first, but the script does not enforce that the database is quiescent.

**Reproduction:** Create a baseline backup, commit one more row while WAL is active, then run restore.

```text
beforeRestore: 2 rows
committedWalBytes: 4152
restoreExit: 0
restoredRows: ["baseline"]
safetyCopyRows: ["baseline"]
```

**Impact:** If restore is run while the service is live, or before WAL checkpoint, committed transactions after the backup can be lost. The “safety copy” may not contain them either.

**Remediation:**

- Use SQLite’s online backup API for the safety copy, not `copyFileSync` of the main file.
- Refuse restore if the POS service is running or the database is not quiescent.
- Checkpoint/truncate WAL safely before destructive replacement.
- Validate backup mode and supported schema range, not only `version >= 2`.
- Add a restore drill that commits data after backup and proves the safety copy preserves it.

**Verification required:** Restore must either preserve all committed pre-restore data in the safety copy or refuse to run.

### F-06 — High — Docker image cannot build from a clean checkout

**Status:** Confirmed by inspection; Docker was unavailable for an actual build.

**Evidence:**

- `Dockerfile:8` builds `dist` in the build stage.
- `Dockerfile:16` uses `COPY --chown=node:node dist ./dist` in the runtime stage.
- That COPY reads from the build context, not the build stage.
- `.dockerignore:2` excludes `dist` from the build context.

**Impact:** The documented Docker/Caddy deployment path fails on a clean checkout because `dist` is absent from the context.

**Remediation:**

```dockerfile
COPY --from=build --chown=node:node /app/dist ./dist
```

- Add a CI job that builds the Docker image.
- Optionally run a container smoke test against `/api/health`.

**Verification required:** `docker compose build` must succeed from a clean checkout.

### F-07 — Medium — Reconciliation sweep can starve newer interrupted sales

**Status:** Confirmed.

**Evidence:**

- `server/sales.js:180-182` selects `creating`, `needs_reconciliation`, `awaiting_payment`, and old `paid` rows ordered only by `updated_at ASC LIMIT 20`.
- Successful reconciliation of unchanged `awaiting_payment` rows may not advance them out of the candidate set.

**Reproduction:** Create 21 pending sales, mark the newest `needs_reconciliation`, run the sweep.

```text
checked=20
reconciled=20
newestNeedsReview=needs_reconciliation
```

**Impact:** A backlog of ordinary pending sales can prevent interrupted sales from being reconciled automatically.

**Remediation:**

- Prioritize `needs_reconciliation` and `creating` over ordinary `awaiting_payment`.
- Track `last_reconciled_at` / attempt count and use round-robin or priority queues.
- Exclude healthy awaiting-payment orders from the same limited sweep or give them a separate cadence.
- Add a starvation regression test.

### F-08 — Medium — Refund lifecycle produces inconsistent order, product, and shift metrics

**Status:** Confirmed.

**Evidence:**

- `server/sales.js:47-49` maps refunded Woo orders back to local `paid`.
- `server/app.js:180-188` nets total revenue but still counts refunded orders/items and gross top-product totals.
- `server/shifts.js:27-43` dynamically nets refunds for open shifts, while closed shifts keep `expected_cash` but recompute summary net/cash.

**Reproduction:** Pay a GHS 115 cash sale, close the shift, fully refund in fake Woo, reconcile.

```text
saleStatus=paid
refunded=11500
report.total=0
report.orders=1
report.items=1
report.topProducts[0].total=10000
closedShift.expectedBefore=21500
closedShift.expectedAfter=21500
closedShift.netAfter=0
closedShift.cashAfter=0
```

**Impact:** Fully refunded sales still appear as paid orders/items sold; top products remain gross; closed-shift summary and expected cash can disagree after later refunds.

**Remediation:**

- Add explicit `refunded` / `partially_refunded` local states or a separate refund ledger.
- Report gross, refunded, and net quantities/amounts consistently.
- Decide whether closed shifts are immutable historical snapshots; if so, do not dynamically change their summary, and record post-close refunds as adjustments.
- Add full/partial refund tests across report, CSV, receipt, and shift views.

### F-09 — Medium — `sold_individually` can be bypassed with duplicate lines

**Status:** Confirmed.

**Evidence:**

- `server/catalog.js:66` checks `line.quantity > 1` per line.
- It does not aggregate duplicate product/variation lines before the sold-individually check.

**Reproduction:** Send two lines of the same sold-individually product, quantity 1 each.

```text
prepare=201
lines=2
qty=2
```

**Impact:** API clients can bypass a WooCommerce purchase restriction. The UI normally merges lines, but the server must enforce the rule independently.

**Remediation:** Aggregate quantities by product/variation before validation and reject totals greater than one for sold-individually products.

### F-10 — Medium — In-stock variation under an out-of-stock parent is accepted

**Status:** Confirmed with a fake Woo fixture.

**Evidence:**

- `server/woocommerce.js:139-152` uses the variation as the availability source.
- `server/catalog.js:63-78` does not reject a variable product whose parent is explicitly `outofstock`.

**Reproduction:** Parent `stock_status=outofstock`, variation `stock_status=instock`.

```text
prepare=201
status=awaiting_payment
```

**Impact:** The POS may sell a variation that the storefront treats as unavailable, depending on Woo theme/plugin stock behavior.

**Remediation:**

- Define and test the intended parent/variation stock policy.
- If parent out-of-stock is authoritative, block checkout.
- If variation stock is authoritative, document and verify against the actual Woo installation.

### F-11 — Medium — Sales history and reports silently truncate large datasets

**Status:** Confirmed.

**Evidence:**

- `server/app.js:159` returns sales with default limit 250.
- `server/app.js:180` and `server/app.js:192` build reports/CSV from `sales.list(user, 10000)`.

**Reproduction:** Insert 10,002 paid rows.


**Impact:** Reports and exports can silently omit transactions once volume exceeds the fixed limit.

**Remediation:**

- Use SQL aggregation for reports and exports.
- Add pagination/cursors for sales history.
- Return explicit truncation metadata if a limit is ever reached.
- Add a high-volume report test.

### F-13 — Medium — Full-card-number reference filter can be bypassed with separators

**Status:** Confirmed.

**Evidence:** `server/sales.js:18` strips whitespace only before matching 13–19 digits.

```text
"4111111111111111"      REJECTED
"4111 1111 1111 1111"   REJECTED
"4111-1111-1111-1111"   ACCEPTED
"4111.1111.1111.1111"   ACCEPTED
```

**Impact:** A cashier can accidentally paste a full PAN into a payment reference, contrary to the stated payment boundary.

**Remediation:**

- Normalize all non-digits before checking for PAN-like sequences.
- Reject common separated PAN formats and add UI guidance.
- Keep the field labelled strictly as merchant/terminal reference.

### F-15 — Low — Idempotency fingerprint ignores the sale note

**Status:** Confirmed.

### F-16 — Low — CSV formula guard misses some leading control/whitespace cases

**Status:** Confirmed at the helper level.

**Evidence:** `server/app.js:193` checks only leading `= + @ - \t \r`.

```text
" =1+1"      -> not prefixed
"\n=1+1"     -> not prefixed
"\u0000=1+1" -> not prefixed
"=1+1"       -> prefixed
```

Most exported user-controlled fields are trimmed by Zod, so exploitability is limited. This is defense-in-depth.

**Remediation:** Trim/normalize before checking, reject control characters, and prefix any cell that could be interpreted as a formula by spreadsheet software.

### F-17 — Low — Origin validation is host-only and non-production trusts forwarded host

**Status:** Confirmed by inspection and helper probe.

**Evidence:**

- `server/app.js:75-83` compares `parsed.host`, not full origin.
- When `POS_PUBLIC_ORIGIN` is unset, allowed hosts include `x-forwarded-host`.
- `server/config.js:52` defaults non-production trust proxy to `1`.

Probe:

```text
https://pos.example.com      allowed
http://pos.example.com       allowed
https://pos.example.com:8443 rejected
https://evil.example         rejected
```

**Impact:** Production staging/live requires `POS_PUBLIC_ORIGIN`, which reduces risk. Non-production or misconfigured deployments have weaker origin/proxy assumptions.

**Remediation:**

- Compare scheme + host + port against the configured public origin.
- Require `POS_PUBLIC_ORIGIN` for any network-exposed staging/live instance.
- Trust only the exact reverse-proxy hop count and document direct-port restrictions.

### F-19 — Low — Non-hashed static assets are cached as immutable for one year

**Status:** Confirmed by inspection.

**Evidence:** `server/index.js:17-22` applies `maxAge: '1y', immutable: true` to all static files, with an exception only for HTML.

### F-20 — Low — Expired/revoked sessions and forced-password flow leave a confusing UI state

**Status:** Partially confirmed by browser probe and inspection.

**Evidence:**

- `src/api.js:6-7` throws on 401 but does not notify the app to clear session state.
- `src/App.jsx:39-40` refreshes when `session.user.id` changes, not when `mustChangePassword` changes.
- During forced-password bootstrap, initial catalogue/sales/shift requests can return 403; after password change, the same user ID does not automatically retrigger refresh.

Browser probe after session revocation:

```text
API /api/catalog: 401
loginForms: 0
UI: authenticated shell with "Sign in to continue" error
```

**Impact:** Server authorization still holds, but users can remain in an authenticated-looking shell or need a manual “Try again” after first password change.

**Remediation:**

- Broadcast 401/403 session errors to App and return to login when appropriate.
- After successful forced-password change, explicitly refresh catalogue/sales/shift.
- Add browser tests for bootstrap password change, idle expiry, and owner revocation.

## Additional observations and unverified risks

These were inspected but not fully reproduced against a real WooCommerce staging store:

1. **No stock reservation between prepare and pay.** Woo pending-order stock behavior must be verified on the actual store, especially concurrent online/POS last-item purchases.
2. **`findOrderByKey` searches at most 10 × 100 orders.** On a busy store, an interrupted order may fall outside the search window.
3. **Synchronous scrypt blocks the event loop.** Login/reset bursts can delay other requests; consider async scrypt or a worker pool.
4. **Demo auth creates unbounded sessions.** Rate limiting reduces but does not eliminate storage growth in a public demo.
5. **`paid_at` construction appends `Z` unconditionally.** Verify Woo GMT field format to avoid double-`Z` timestamps.
6. **nginx read timeout is 30 s.** Woo GET retries can approach/exceed that under failure; align proxy and application timeouts.
7. **Preflight checks Node major version only.** It should enforce the documented minimum minor version.
8. **Restore accepts any schema version ≥ 2 and does not validate backup mode.** Future-schema or wrong-mode backups should be rejected.
9. **Backup retention is local-only.** Off-host encrypted backup and WordPress backup remain operator responsibilities.
10. **Single-instance design.** In-process locks and SQLite are appropriate for one shop/one server, but horizontal scaling requires redesign.
